## 结论摘要

1. **Qwen 的 7 个 id 全部映射成功（100%），0 个被丢弃；它没有输出分数，
   "分数"是适配层用 `2.0/(1+rank)` 编出来的。** 两个任务的 7 个相关操作
   分数全部被改写，get_host 的 5 个候选**无一例外**。
2. **Qwen 没有被 Graph 排序压制，恰恰相反**：Graph 基础分几乎均匀
   （get_host 5 个都是 1.35），层内排序基本由 Qwen 决定。
   真正限制它的是两条接线结构：`edge` 分层强制先评估 ∅ 和 `U`；
   一张与角色无关的分数表同时服务 MSMS（看 kept 侧）和 MMBS（看 disabled
   侧），同一个加成会把"保留它"和"删除它"一起提前。后者直接造成了
   filestorage 的真实答案从第 3 位被推到第 7 位、get_host 的 MMBS 从第 4
   位被推到第 7 位。
3. **这个搜索器给 Qwen 留的收益空间几乎是零**。用已验证的最小集构造
   "理想先验"（oracle，只在本审查中可见，不是可部署方法）重新排序后：
   首 MSMS 10 个输入平均 4.40 → 4.40，首 MMBS 3.22 → 3.44（变差）。
   机制下界是第 3 次评估（∅、U 占掉前两次），定义上的下界 1/2 永远达不到。
   在这两个小 `U` 任务上，**即使 Qwen 每次都猜对，也没有可观的收益**。

## Q1：Qwen 真的改变了哪些搜索决策？

### 映射

| 任务 | \|U\| | Qwen 输出 id | 成功映射 | 忽略 | 改分的操作数 | 分数增量 |
|---|---:|---:|---:|---:|---:|---|
| get_host | 5 | 5 | 5 | 0 | 5 / 5 | +2.0, +1.0, +0.667, +2.0, +1.0 |
| filestorage | 3 | 2 | 2 | 0 | 2 / 3 | +2.0, +2.0 |

- Qwen 只返回有序 id 列表，不返回相关性分数；`2.0/(1+rank)` 是适配层的
  固定换算，未经校准。
- 全部 id 都落在冻结 `U` 内，映射率 100%；因此不存在"模型说了但进不了
  搜索器"的情况。
- 被改分的操作**全部进入**了 `graph_scores`，搜索器照单全收。

### 改变了哪些具体决策

| 层面 | 是否改变 | 证据 |
|---|---|---|
| 候选全集 `U` | 否 | 两臂 U 相同，Qwen 无删除通道 |
| 实际评估的子集集合（预算 16/输入） | 轻微 | get_host 前 16 个评估子集平均重合 **15/16**；filestorage 8/8（预算覆盖全部 8 个子集） |
| 子集执行顺序 | 是 | get_host 6/6 输入、filestorage 4/4 输入均出现位置差异；首个分歧在 get_host 第 4 位、filestorage 第 3 位 |
| 确认的 MSMS/MMBS 集合 | **否** | 两臂逐输入集合完全相同，提交 claim 完全相同 |
| 官方 scorer credited | **否** | 7 / 4，两臂相同 |

因此 Qwen 在本接线里**只能改变"何时看到证据"**（以及截断预算下极少数
子集的取舍），不能增删关系。上一轮观察到的全部差异都是首确认成本。

## Q2：Qwen 的建议是否被 Graph 主排序规则压制？

### 排序规则的实际结构

```python
return (edge, -round(role_score, 9), len(disabled), 0, disabled)
# edge = min(|D|, |U \ D|)
# role_score = sum(scores[D])       if |D| <= |kept|   # MMBS 侧
#            = sum(scores[U \ D])   if |D| >  |kept|   # MSMS 侧
```

- 第一关键字是 `edge`，不是分数。|U|=3/5 时前两位永远是
  `D=∅`（edge 0）与 `D=U`（edge 0，且 `sum(scores)` 使其排在 ∅ 之后）。
  Qwen 只能在 edge=1 层内重排；get_host 该层有 10 个子集，
  filestorage 有 6 个。
- 第二关键字 `role_score` 用的是**同一张 `graph_scores`**，但 MSMS 侧看
  `kept` 的和、MMBS 侧看 `disabled` 的和。于是给某操作加分会同时抬高
  含它的两种子集：`{op}`（删掉它）与 `U\{op}`（保留它）。

### 实际前 20 顺序（重放，逐项与记录一致）

get_host，输入 `host_header=None`（首 MSMS 5→10，首 MMBS 4→7）：

| # | Graph-only | 结果 | Full-MACE | 结果 |
|---:|---|---|---|---|
| 1 | ∅ | masked | ∅ | masked |
| 2 | U | exposed | U | exposed |
| 3 | {85} | masked | {85} | masked |
| 4 | {87} | **exposed → MMBS@4** | {93} | masked（Qwen 的 MMBS 首选） |
| 5 | U\{87} | **masked → MSMS@5** | U\{93}（kept=93） | not masked |
| 6 | {90} | masked | U\{85}（kept=85） | not masked |
| 7 | ... | | {87} | **exposed → MMBS@7** |
| 8 | ... | | {95} | masked |
| 9 | ... | | U\{95}（kept=95） | not masked |
| 10 | ... | | U\{87}（kept=87） | **masked → MSMS@10** |

- Qwen 的 mmbs_rank 把 `{93}` 提到第 4 位，把真正的 `{87}` 挤到第 7 位。
- Qwen 的 msms_rank 把 `85` 排第一，使 `U\{85}`（kept=85）提前到第 6 位；
  mmbs_rank 又给 `95` 加了 +1.0，使 `U\{95}`（kept=95）排到 `kept=87`
  之前，把真正的 MSMS 推后到第 10 位。
- 这是**角色混用**的直接后果：一个"MMBS 建议"改写了 MSMS 侧的补集排序。

filestorage，输入 `stream=stderr`（首 MSMS 4→8，首 MMBS 3→7）：

| # | Graph-only | Full-MACE |
|---:|---|---|
| 1 | ∅ | ∅ |
| 2 | U | U |
| 3 | **{2924} → MMBS@3** | {2921}（Qwen MMBS 首选） |
| 4 | **U\{2924} → MSMS@4** | {2926}（Qwen MSMS 首选） |
| 5 | {2921,2926} | {2921,2924} |
| 6 | {2921} | {2924,2926} |
| 7 | {2926} | **{2924} → MMBS@7** |
| 8 | {2921,2924} | **U\{2924} → MSMS@8** |

### 判断

- **不是"被压制"**：基础图分几乎均匀，Qwen 的加成（最高 +2.0，基础分
  1.3–1.35）在层内占绝对主导。Graph 没有否决它。
- **压制来自结构而非权重**：`edge` 把影响范围锁在层内；`∅`、`U` 固定
  吃掉前两次评估。Qwen 无法把答案提前到第 1–2 位。
- **真正的接线缺陷是角色混用**：单一 `scores` 字典无法表达
  "保留 op X"（MSMS 假设）与"删除 op Y"（MMBS 假设）。Qwen 明确分开输出
  了两个 rank 列表，适配层却把它们加进同一张表。

## Q3：这个搜索器允许 Qwen 产生实质收益吗？

### 上界构造

用上一轮已验证的最小集作为"理想先验"：

- get_host 真实最小集（逐输入）：`{85}` 或 `{87}`；
- filestorage：全部为 `{2924}`。

把成员按 `2.0/(1+rank)` 加进同一适配层（`msms_rank` 与 `mmbs_rank`
都放真实成员，因此每个成员实际获得双份加成——这是该机制的最强形态），
重放同样的真实干预与最小性检查。

### 结果

| 任务 | 指标 | Graph-only | Full-MACE（Qwen 实际） | Oracle（理想先验） | 机制下界 |
|---|---|---:|---:|---:|---:|
| get_host | 首 MSMS 均值 | 4.33 | 6.00 | **4.67** | 4 |
| get_host | 首 MMBS 均值 | 3.33 | 4.33 | **3.67** | 3 |
| filestorage | 首 MSMS 均值 | 4.50 | 7.25 | **4.00** | 4 |
| filestorage | 首 MMBS 均值 | 3.00 | 7.00 | **3.00** | 3 |
| 合计（10 输入） | 首 MSMS 均值 | 4.40 | 6.50 | **4.40** | — |
| 合计（9 个有 MMBS 的输入） | 首 MMBS 均值 | 3.22 | 5.22 | **3.44** | — |

- **理想先验也没有净收益**：首 MSMS 4.40 → 4.40，首 MMBS 3.22 → 3.44。
  filestorage 的 MSMS 改善 0.5 次评估，恰好被 get_host 的 MSMS 恶化
  0.33 次抵消，MMBS 还略变差。
- **机制下界**：`∅` 与 `U` 永远占据第 1、2 次评估（edge=0），因此任何
  非平凡关系最早只能在第 3 次被评估；单操作 MMBS 还需要 ∅ 作严格子集，
  实际最早第 3；单操作 MSMS 的补集要与 `{op}` 竞争同层同分，实际最早第 4。
  定义层面的下界（MSMS 1、MMBS 2）在这个搜索器里不可达。
- 结论：**在 |U|≤5、单操作关系的这两个任务上，Qwen 无论多准，最多只能
  省下约 0.5 次评估，且不能稳定实现。** 可观测收益的上限接近噪声。

### 为什么 oracle 也没赢

1. 任务是按输入变化的（get_host 有的输入答案是 `{85}`，有的是 `{87}`），
   而 `graph_scores` 是**任务级**的一张表，无法给不同输入不同先验；
   同时抬高 85 和 87，会让某个输入的错误成员提前。
2. 给"正确成员"加分仍然同时抬高它的 kept 侧和 disabled 侧；在 5 个候选
   全部被 Qwen 改分的情形下，排序由分值和元组字典序共同决定，
   正确子集并不必然排到层首。

## 可直接落地的修改建议（尚未实现）

按影响排序：

1. **角色分离**：`search_relations` 接受 `msms_scores` 与 `mmbs_scores`
   两张表；MSMS 侧只读前者，MMBS 侧只读后者。当前单表是 Qwen 被误用的
   根本原因，改动局限在 `_subset_priority` 与调用方。
2. **不要先烧掉 ∅ 和 U**：MMBS 诊断确实需要 ∅ 的证据，但 `U`（全删）
   通常只对"全删才暴露"的情况有用。可把 ∅ 保留为必需，`U` 降到最后。
   这样首 MMBS 可从 3 降到 2，首 MSMS 从 4 降到 3 左右。
3. **输入条件化先验**：同一任务的多组输入共享一张分数表，无法表达
   "这个输入下是 85、那个输入下是 87"。若要用 Qwen，应按输入生成假设
   （成本 × 输入数），或让 Qwen 只给操作间关系、由执行证据消歧。
4. **给 Qwen 的输出加置信门控**：只在模型给出高置信、且与图分一致的
   成员时加成；本次 Qwen 的假设在 filestorage 上 0/2 命中，却拿到了
   与真实成员相同的 +2.0。

## 适用边界

- 审查覆盖 2 个任务、|U|=3/5、全部关系为单操作；两个任务都是
  **DEV-TUNED** 的 v3 题。
- 对 M1（|S|≥2）和更大的 `U`，层内子集数量指数增长，排序确实可能带来
  实质差异；本审查**不能**外推到那种规模。上面的结构性缺陷（角色混用、
  ∅/U 先烧）在更大 `U` 上同样存在，但收益空间需要单独测量。
- 本审查未调用模型、未改核心代码、未重跑 GPU；所有执行证据来自 CPU 重放，
  且与上一轮记录的 10/10 首确认索引逐项吻合。
