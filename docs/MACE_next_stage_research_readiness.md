### 1.2 冻结规则

**候选发现（`ast_discovery.py`）**

1. 定位包含目标行的函数；
2. 沿同文件调用名（含 `self.method` 的名字匹配）得到有界可达函数集；
3. 候选操作 = 写入与 A **同一普通变量**（`Name` 目标，不含属性/容器元素）
   的赋值语句；
4. A 自己函数内只取 A 之后的赋值；可达辅助函数内不受位置限制；
5. 包含这类赋值、且内部没有其他候选的 `if` 块在规则中列为候选，但
   重叠排除规则会去掉任何包含已收集赋值的块；**本轮 16 个候选全部是
   赋值语句**，没有 `if` 块候选；
6. 用公开输入网格做单操作删除，按观察变化数排序、按行为签名去重、
   丢弃零效应，保留至多 6 个。

**操作干预（`execution.py`）**

- 每个子集构造一个完整项目树副本；语句替换为等缩进 `pass`，多行语句
  和块整段替换；
- 探针是冻结的公开 probe 脚本，输入为 JSON；观察由 probe 返回；
- 用 `sys.settrace` 检查 A 在提交输入上确实执行；
- 所有探针执行与变体构建都缓存在单题 Executor 内。

**关系判定（`execution.py` + `baseline_c.py`）**

- 对给定输入，枚举所给操作全集 `U_C` 的**全部**子集（含空集），
  plus/minus 各执行一次；
- `masked[D]` / `exposed[D]` 都按“被禁用集合 D”索引；
- MSMS：非空保留集 S，`Masked_strict(U\S)` 且无更小的非空充分子集；
- MMBS：非空禁用集 S，`Exposed(S)` 且无更小的破除子集（含空集检查）；
- 只有“每个成员在该输入上单独删除都会改变观察”的最小集才被提交；
  否则不提交；
- MSMS 分组只在该输入存在非空 MMBS 时进行（评分器同样要求可观察的
  非空破除集，避免空洞掩盖）；
- ≥2 个不同输入支持 → `FINITE_DOMAIN_EXACT`；单输入 →
  `WITNESS_VERIFIED`；
- 前置关系：从 MSMS 组出发，找一个不同输入作为 control，使同一集合
  在该输入上不是 MMBS；每题最多 2 条；这是双 witness 构造，不是逻辑
  条件归纳。

**UNKNOWN 处理**

- 逐输入记录“masked 但没有因果活跃最小集”等情况到
  `baseline_c.json` 的 `unknowns`；
- 不把无证据关系写进 submission；
- submission 格式没有 UNKNOWN claim 类型，因此 UNKNOWN 不会出现在
  评分器输入里。

## 3. 工作三：独立跨项目测试规划

本节是规划，不是已建成的测试集。目标：在**未参与规则设计**的独立
开源项目上，检验第 1 节冻结基线的真实边界。

### 3.1 沿用 v3 的冻结与隔离原则

1. 每题有公开包（`task.json` + 目标源文件）与隐藏包（U、witness、参考
   关系、证据）；
2. 评分器重跑 P+/P− 与子集枚举，不信任提交的期望状态；
3. 公开包做泄漏检查，不包含 U、witness、参考关系；
4. `T_task` 只按 P+ 覆盖确定，不看 P− 或模型结果；
5. 资格判定与筛选预算按代码强制，不按算法表现调整；
6. 所有结论只对“声明的有限输入 + 声明的 U”成立，不授予 `PROVEN`；
7. 参考关系冻结后，任何更正另开版本化记录，不静默覆盖。

### 3.2 项目池（预注册，不按算法表现挑选）

开发集项目 Jinja2 3.1.3 与 Werkzeug 2.2.3 全部排除。初始项目池为 10 个
独立、纯 Python 为主、测试套件可运行的项目（版本在冻结时从 PyPI 固定并
记录 sdist/wheel 哈希）：

```
urllib3, requests, starlette, httpx, attrs,
sqlalchemy, python-dateutil, rich, packaging, more-itertools
```

排除理由必须逐项记录，例如 C 扩展导致构建不可复现、异步探针无法稳定
观察、生成代码占比过高、与开发集共享上游代码等。项目池不按“哪个项目
更容易出题”增删；如果某项目在统一漏斗下没有合格候选，记录为 0，不用
其他项目替换其配额。

### 3.3 漏斗与预算

沿用 v3 的漏斗形状，但扩展静态扫描的形状以覆盖新机制：

```
静态扫描（全部函数/方法）
  → 去重候选
  → P+ 测试覆盖筛选（T_task 只看 P+）
  → targeted P− 删除筛查（预算内全部审查）
  → 全套件 P− 存活筛查
  → 隐藏 U 枚举与机制验证
  → 资格判定（机制定义 + MSMS/MMBS/条件证据）
  → 按机制分层配额选取
  → 建公开/隐藏包、泄漏检查、冻结
```

预算（初版，代码强制）：

| 项 | 预算 |
|---|---:|
| 静态去重候选审查 | 2000–2500 |
| targeted P− 运行 | 600–800 |
| 全套件 P− 运行 | 100–150 |
| 目标合格题 | 15（5 机制 × 3） |
| 机制分层过采样 | 30 个存活候选 |

预算依据：v3 的 403 个静态候选中 29 个存活、5 个合格（1.2%）。按同一
比例，15 道题约需 1250 个静态候选；新机制可能更稀有，因此预算上浮到
2000–2500，并保留 2× 过采样。若某机制在预算内不足 3 题，报告缺口，
**不降低机制定义、不人工替换样本**。

### 3.4 五类机制的操作定义

这些定义写在隐藏参考中，不进入公开包；每题必须由独立验收脚本重新
执行确认，不能复用 C 的代码。

**M1 真正协同掩盖（true collaboration）**

- 存在输入 x 和最小 MSMS（或 MMBS）集合 S，`|S| ≥ 2`；
- S 的任意真子集在 x 上都不是充分/破除集；
- 至少一个成员 s∈S 在 x 上满足：单独禁用 s 时，plus 与 minus 两侧的
  观察都与“不进一步禁用 s”时相同（individually inert），以区别于多个
  独立 masker 的并列；
- 该 inert 成员正是现有提交过滤 `allowed()` 会丢弃的对象；定义本身是
  机制属性，不依赖 C 的实现；
- 参考记录 x、S、每个成员的单独干预结果（两侧）。

**M2 多条后备路径（multiple fallbacks）**

- 至少两个不同的最小集合 S1、S2（可为单元素），各自在某个 witness 上
  成立；
- S1、S2 互不为子集；
- 参考分别记录两个 witness，证明不是同一条路径的重复。

**M3 跨函数状态与对象别名（cross-function state / aliasing）**

- A 与至少一个 masker 位于不同函数或不同模块；
- 关系通过对象状态、属性或别名传播，probe 观察的是该状态；
- 参考记录调用链与状态字段；验收确认删除 masker 后状态观察改变。

**M4 循环与有状态执行（loops / stateful execution）**

- 在 witness 上 A 执行 ≥2 次（trace 计数）；
- 掩盖/暴露依赖迭代次数或迭代顺序；删除 masker 会改变后续迭代的观察；
- 参考记录执行次数与逐次观察；
- 需要把现有 trace 从“是否执行”的布尔值扩展为逐次计数；这是验收工具
  改动，不是算法改动。

**M5 条件缺失及复杂布尔组合（missing conditions / complex booleans）**

- 关系只在某个布尔条件成立时出现；
- 条件至少涉及两个输入谓词（合取/析取/否定组合）；
- 参考包含至少一对 boundary 输入：一个满足条件（关系成立），一个只
  改变一个谓词（关系不成立），且最小集合相同。

### 3.5 选择独立性协议

为防止“为了让算法失败或成功而选题”：

1. 项目池、版本、扫描规则、预算、配额、随机种子在任何候选结果产生
   之前写入预注册文件；
2. 静态扫描与 targeted 筛查对预算内**所有**候选执行，记录全部拒绝
   理由，不按结果挑选；
3. 机制分类由隐藏参考构造与独立验收完成，**分类时不运行 C、A、B**；
4. 每个机制分层内，用预注册种子对候选 ID 做哈希排序，取前 3 个；
   不按“看起来适合某方法”排序；
5. 若某层不足 3 题，记录缺口；不跨层替补，不放宽定义；
6. 测试集冻结（公开包、隐藏包、manifest、SHA256SUMS）之后才允许运行
   任何基线；
7. 基线只运行一次；不得用测试分数回头改 C 的规则、输入网格或 prompt；
8. 发现 harness bug 时，区分“工具错误”与“方法调优”：工具错误可修正
   并重跑，方法调优视为新实验版本，两个版本都报告。

### 3.6 验收与隔离

每题沿用 v3 的十项验收，另加机制专项：

| 检查 | 内容 |
|---|---|
| source_and_single_line_diff | P+/P− 仅在目标文件目标行不同 |
| deletion_record | 原行与替换行逐字记录 |
| candidate_universe_positions | U 的位置/代码与源码一致 |
| target_execution | witness 输入下 A 确实执行 |
| matrix_reproduction | 独立重算矩阵与存档一致 |
| minimality | 枚举 U 全部子集，无更小有效子集 |
| mechanism_specific | M1–M5 的定义检查（上方） |
| p_minus_full_suite | P− 上项目适用套件通过 |
| t_task_on_p_plus | 冻结 T_task 在 P+ 通过 |
| t_task_executes_A | T_task trace 确认执行 A |
| leak_check | 公开包不含 U/witness/参考关系 |

隔离：HIDDEN 不进入任何基线输入、候选生成或参数调整；评分器子进程
调用；参考比对只在评估侧。

### 3.7 指标与报告口径

- 分层报告：每机制的任务数、参考关系数、credited 关系数、FALSE、
  UNVERIFIED、INVALID、UNKNOWN、证据等级；
- 证据等级分开：witness 级、有限域级、全域证明（本轮及可预见阶段为 0）；
- 资源：探针执行、变体构建、wall time、模型调用/token（若 A/B 运行）；
- n 很小（每层 3 题），只报告原始计数与逐题表，不做显著性宣称。

### 3.8 风险与停止规则

- 某机制零合格题：报告 `NO_QUALIFIED_TASK`，不造题；
- 项目环境不可复现：移出项目池并记录，不换成“更容易”的项目；
- 异步/线程导致观察不稳定：该题标 INCONCLUSIVE，不进入测试集；
- 参考关系有争议：进入人工复核；未达成一致的题不进测试集；
- 基线在测试集上出现 harness 级失败：修 harness，重跑并记录；
  方法级失败：作为结果报告，不调参。

## 4. 工作四：能力对照矩阵

### 4.1 矩阵

`NOT_MEASURED` = 因真实模型不可用，本轮没有任何可引用数据；
`接口能力` = 从代码与提交格式能确定的、与模型表现无关的能力。

| 能力 | A Direct Qwen | B Qwen + Verifier | C 冻结基线 |
|---|---|---|---|
| 候选操作发现 | `NOT_MEASURED`（接口允许提交任意位置） | 无；只接收 proposal 命名的操作 | 有界规则：同变量赋值 + 同文件可达函数；本轮 16 候选全部为赋值 |
| 操作干预执行 | 无（模型不执行） | 有，复用同一 Executor | 有，P+/P− 变体 + 冻结 probe |
| 独立关系 | `NOT_MEASURED` | 可验证 | 有；get_host 85/87 两个独立最小集 |
| 协同关系 | `NOT_MEASURED` | 可验证（若 proposal 命名） | 搜索空间支持多元素集，但提交过滤要求每个成员单独活跃；**实际会丢弃真协同集** |
| 多条后备路径 | `NOT_MEASURED` | 可验证 | 可枚举多个最小集；无“后备路径”专门建模；jinja 的 137 是唯一 masker |
| 跨函数状态/别名 | `NOT_MEASURED` | 可验证 | 只跟同文件调用名；不跟跨文件、动态派发、属性/别名状态 |
| 循环/有状态执行 | `NOT_MEASURED` | 可验证（按输入执行） | 执行层能观察，但发现/归因不区分迭代，无循环感知 |
| MSMS/MMBS 搜索 | `NOT_MEASURED` | 仅在 proposal 全集上枚举 | 在 `U_C` 上**完整枚举全部子集**（含空集） |
| 最小性验证 | `NOT_MEASURED` | 有（有限输入 + proposal 全集） | 有（有限输入 + `U_C`） |
| 条件发现/生成 | `NOT_MEASURED` | 只验证，不生成 | 固定输入网格；无合成、无反例驱动 |
| 前置关系 | `NOT_MEASURED` | 可验证双输入模式 | 双 witness 构造，每题最多 2 条；非逻辑归纳 |
| UNKNOWN 处理 | `NOT_MEASURED` | 输出 VERIFIED/REFUTED/UNKNOWN | 逐输入记录 unknown，不提交无证据关系；无 claim 级 UNKNOWN |
| 测试级分类 | 无接口 | 无接口 | 无接口 |
| 全域证明 | 无 | 无 | 无 |

### 4.2 C 是否已有完整 MSMS/MMBS 搜索能力

**是，但“完整”必须限定三个范围；超出范围就不完整。**

已实现且可验证：

- `Executor.relations()` 对传入的 `ids` 枚举 `2^n` 个禁用子集（含空集），
  plus/minus 各执行一次；
- `_minimal_masked` 对每个非空保留集检查 `Masked_strict(U\S)`，并检查
  所有真子集，得到最小充分集；
- `_minimal_exposed` 对每个非空禁用集检查 `Exposed(S)`，并检查所有
  真子集（含空集），得到最小破除集；
- 键的语义与评分器一致：masked/exposed 都按**被禁用集合**索引；
- 开发集 5 题的 18 条参考关系全部通过评分器的最小性检查，另有 5 条
  参考外关系被确认。

不完整的部分：

1. **范围一：U**。只对 `U_C` 完整；`U_C` 由同变量赋值规则发现，漏掉
   的操作永远不会被枚举。开发集 `U_C ⊇ U_hidden`（5/5）是规则调试的
   结果，不是保证。
2. **范围二：输入**。只对提交的有限输入网格完整；不是 legal input
   domain 的完整搜索。
3. **范围三：提交过滤**。`allowed()` 要求最小集每个成员在**该输入**
   上单独删除就改变观察。MSMS/MMBS 的定义本身不要求这一点；真正的
   协同集（成员单独惰性、联合有效）会在这一步被丢弃。因此“枚举完整”
   不等于“提交完整”。

准确表述：**C 在给定有限 universe 与有限输入上实现了评分器语义的完整
子集搜索和最小性验证；它的发现范围与提交规则都不完整。**

### 4.3 C 是否支持反例驱动新增条件

**不支持。** 证据：

- `inputs.py` 是每题固定的 6–8 个输入列表；
- `baseline_c.run()` 单遍遍历该列表，没有生成、变异或迭代搜索；
- 没有任何代码把“某个输入上关系不成立”反馈成新输入；
- 暴露输入只作为 witness 提交，不用于条件细化；
- 前置关系只是从固定网格里挑一个 control 输入，不推断谓词。

因此，本开发集的 4 条 input 级 UNKNOWN（filestorage 3、secure 1）不会
被 C 自己消解；`FILESTORAGE` 的 MSMS 只停在 witness 级也是同一原因。

### 4.4 过多干预与成本

| 题目 | `U_C` | 输入 / masked | 探针 | 变体 | wall (s) | 探针/credited 关系 |
|---|---:|---:|---:|---:|---:|---:|
| jinja2 | 1 | 6 / 4 | 24 | 4 | 10.35 | 6.0 |
| bind | 2 | 7 / 5 | 76 | 12 | 28.96 | 19.0 |
| filestorage | 3 | 6 / 4 | 80 | 16 | 30.04 | 20.0 |
| get_host | 5 | 7 / 6 | 396 | 64 | 124.43 | 56.6 |
| secure | 3 | 8 / 7 | 120 | 16 | 38.16 | 30.0 |
| **合计** | — | **34 / 26** | **696** | **112** | **231.94** | **30.3** |

成本结构：

- 子集枚举是 `2^|U_C|`，每个子集 plus/minus 各一次；`|U_C|=5` 时单输入
  就可能有 64 次执行；
- 变体构建要复制整个项目树，112 次构建是主要 I/O 成本；
- 资源随候选数指数增长。若 `|U_C|=6`，子集数翻倍；若输入数从 7 增到
  8，再乘 8/7；预算 6000 在单题内仍够，但多题总成本会到小时级。

“过多干预”的具体形态：get_host 为 7 条关系执行 396 次探针（56.6 次/
关系），其中大量用于枚举与剪枝；对小 universe 这是可接受的，但对
跨项目批量运行不经济。

### 4.5 错误归因、缺失条件与 UNKNOWN

开发集结果：

- `FALSE = 0`、`UNVERIFIED = 0`、`INVALID = 0`、`DUPLICATE = 0`；
- claim 级 UNKNOWN = 0；
- input 级 UNKNOWN = 4（filestorage 3、secure 1）；
- 额外 5 条真前置关系未被参考收录，说明参考不穷尽，但不是 C 的错误。

结构性风险（未在开发集触发）：

| 风险 | 机制 | 后果 |
|---|---|---|
| `U_C` 漏掉隐藏 U 中的操作 | 同变量赋值规则过窄 | “最小集”在隐藏 U 上不最小 → 可能 FALSE |
| 提交过滤丢弃协同集 | 每成员单独活跃 | 假阴性，关系不会被提交 |
| 固定输入网格不足 | 无合成/反例搜索 | 假阴性 + input 级 UNKNOWN |
| 同文件名匹配的误连 | 只按调用名，不看接收者 | 可能把无关函数纳入候选；效应剪枝通常会丢弃 |
| 块候选被重叠规则排除 | 包含候选赋值的块不单独成操作 | 无法表达“删除整条条件路径”的操作 |
| 多行语句按块删除 | 整段替换 | 语义上是整条语句，不是逐行 |
| 无 claim 级 UNKNOWN | 提交格式限制 | “不知道”只能留在本地日志，评分器看不到 |

## 6. 可能值得研究的新算法缺口

以下只是机会，不是已证有效的机制；不得把 C 已有功能重新包装成创新。

1. **协同关系的发现与提交**：C 的枚举已能产生多元素最小集，但提交
   过滤把它们丢掉。最小验证方式是去掉过滤、看评分器是否确认；这不是
   新架构，只是修正一个已知限制。
2. **反例驱动的条件/输入生成**：从目标函数的分支谓词或暴露输入出发，
   合成能触发/阻断最小集的新输入，直接针对 input 级 UNKNOWN。
3. **跨文件与别名感知的候选发现**：把调用边扩展到跨模块、属性状态、
   容器元素；当前只跟同文件调用名与普通变量赋值。
4. **循环/有状态归因**：记录 A 与候选操作的逐次执行，区分“第 k 次
   迭代才被掩盖”的关系；当前只比较整次 probe 的最终观察。
5. **proposal 补全的 verifier**：在公开源码上独立生成候选全集，再与
   模型 proposal 求交/求差，缓解“模型没提到就验证不到”的盲区。
6. **测试级解释接口**：为“原测试为什么通过”增加 claim 类型；当前
   submission format 不表达，五道题的测试级分类无法被基线评价。
7. **U 之外的可靠性**：在不知道隐藏 U 的前提下，如何报告“相对于我
   发现的全集最小”而不是“全局最小”；可能需要显式的范围声明与
   覆盖度指标。

明确不研究的“伪创新”：

- 把“枚举所有子集并检查最小性”说成新机制——C 已实现；
- 把“用 probe 执行观察”说成新机制——C 已实现；
- 把“先发现候选再验证”说成 MACE 独有——这是基线常规做法。

## 7. 下一阶段最小可验证算法实验（仅设计，未执行）

**EXP-1：最小性-only 提交（minimality-only emission）**

目的：验证“协同关系被提交过滤器丢弃”这一具体假设；不引入新架构。

改动（一行级）：

- 在 `baseline_c.run()` 中，把 `allowed(sets, active)` 替换为恒等过滤，
  直接提交 `executor.relations()` 已算出的全部最小集；
- `active_ops` 仅作为诊断字段保留，不再决定提交；
- 发现规则、输入网格、verifier、预算都不变。

预注册假设：

- **H1（协同恢复）**：在冻结的 M1 协同分层（3 题）上，当前基线提交的
  多元素最小集为 0；改动后至少 2/3 题获得 ≥1 条被评分器确认的多元素
  MSMS/MMBS。
- **H2（开发集回归）**：在五道 DEV-TUNED 题上，改动不新增
  FALSE/INVALID/UNVERIFIED，且 18 条参考关系仍全部被确认。

设计：

1. 先在开发集跑一次回归（只用于 H2，不用于调参）；
2. 在冻结后的 M1 测试集跑一次（只用于 H1）；
3. 两次都记录：credited 关系（按类型与集合大小）、FALSE/INVALID、
   input 级 UNKNOWN、探针数、变体数、wall time；
4. 不增加探针：枚举本来就算出了全部最小集，改动只影响提交。

成功判据：H1 与 H2 同时成立。

失败/停止：

- 开发集出现任何 FALSE：停止，不“修一下再跑开发集”；
- 协同题没有恢复：停止，报告该过滤器不是唯一瓶颈；
- 若出现新的真关系但伴随 FALSE，按“证据质量优先”判失败，并记录
  具体反例。

成本：与现有 C 相同量级的探针/变体；不增加模型调用。

为什么这是最小实验：只改一个提交过滤函数，不新增候选发现、不新增
输入生成、不新增 Prompt/Agent；能直接检验第 4.2 节的“范围三”缺口。

备选实验（依赖模型服务，暂不设计细节）：给 B 增加公开源码的 proposal
补全，测量纯验证对模型 proposal 的增量。等真实 Qwen 可用后再预注册。
